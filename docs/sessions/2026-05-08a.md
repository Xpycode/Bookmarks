# Session: 2026-05-08a

v2 wave 2 — full rebuild of the dashboard view into a draggable, customizable, multi-view "card wall" that's the new primary way of using the app.

## Goal

User reported the v2 wave 1 Dashboard "did not seem to work" — clicking the toggle left the list visible *and* showed an empty `All categories` strip below the sidebar (root cause: 3 children flowing into a 2-column CSS grid). Beyond fixing that, the user wanted a Bookmarkninja-style dashboard: draggable category cards, all bookmarks visible, right-click context menus, custom colors per category, ability to hide categories, and multiple "views" with their own per-view order/hidden set.

Cause was layout, not toggle logic.
- [x] **Phase 1 — dashboard rebuild.**
  - Sidebar **hidden in dashboard mode** via `body.dashboard-mode` class (`body.dashboard-mode .sidebar { display: none }`, `body.dashboard-mode .layout { grid-template-columns: 1fr }`); fixes the row-2 overflow and gives cards full width.
  - **Drag cards by header** — Sortable.js on `.dashboard-grid`, handle `.dash-card-head`. Order persisted via new `set_dashboard_order` API (then `set_view_order` after phase 3).
  - **Drag bookmarks within and between cards** — Sortable.js per-card with shared `group: 'dash-bookmarks'`. Cross-card move is one `reorder_bookmarks` call against the destination's `category_id` (the existing API already accepts that).
  - **Removed the `+ N more` cap.** Card body scrolls internally above `max-height: 360px`.
  - **Right-click context menu** (vanilla JS, `.context-menu` div) for both bookmarks (Open / Edit / Delete) and card headers (Open in list / + Add bookmark / Rename / Delete).
  - **Sortable destroy/recreate** for the grid-level instance to avoid stacked listeners across re-renders.
  - **Sidebar drop-on-category was unaffected** in list mode; in dashboard mode the sidebar is hidden, no conflict.
- [x] **Phase 2 — colors + hide.**
  - New nullable `color TEXT` column on `categories`. **Idempotent ALTER** in new `migrate(PDO)` called from `db()` every request (try/catch swallows the duplicate-column error since SQLite has no `IF NOT EXISTS` for ADD COLUMN).
  - **Per-category color** stored on the row (it's a property of the category, not the view, so it persists across views). Right-click → **Change color…**
  - First color-picker attempt was a programmatic `.click()` on an offscreen `<input type=color>` — **Safari silently blocks that** (anti-spoofing). Replaced with a real `<dialog>` containing a visible color input + Save / Reset to auto / Cancel buttons. Pattern matches existing `#bookmark-dialog`.
  - **Hide-from-dashboard** stored as a JSON id-array in `settings` (key `hidden_ids`) — *not* on the categories table, because hiding is per-view (anticipating phase 3). Right-click toggles; a "Show N hidden" pill in the dashboard meta reveals hidden cards at reduced opacity for un-hiding.
- [x] **Phase 3 — named views.**
  - All view state collapsed into a single `settings.views_data` JSON: `{ views: [{id, name, dashboard_order, hidden_ids}, ...], current_view_id }`. New `ensureViewsData()` PHP helper migrates legacy `dashboard_order` + `hidden_ids` keys into a default "All" view on first call (idempotent — keys preserved as fallback).
  - **Six new API actions:** `add_view` (with optional `clone_from_id`), `rename_view`, `delete_view` (rejects if last view), `set_current_view`, `set_view_order`, `set_view_hidden`. Old `set_dashboard_order` and `set_hidden_ids` removed.
  - **Top-bar dropdown** "View: All ▾" left of the Dashboard button. Reuses the context-menu component (added separator support). Items: each view name (current marked `✓`), `+ New view (clones current)`, Rename / Delete current view. New views default to **clone-of-current** per user's preference.
  - Per-view colors **rejected** (would be visually confusing — MCR shouldn't be red in one view and blue in another). Colors stay per-category-globally.

### Discovered

- **The "live site looks broken" report turned out to be cache.** When the user said "Edge on Windows shows it differently than Safari," the difference was 100% cached `app.js` between browsers (no fingerprinted asset URLs). `app.js` is referenced as `public/app.js` with no `?v=…` query — a deploy-time cache-buster (e.g. file mtime) would prevent this and cost ~5 lines in `views/app.php`.
- **Safari's anti-spoofing silently blocks programmatic native pickers** on offscreen `<input type=color>` / `<input type=file>` elements. Visible-in-viewport is the only reliable trigger. Documented in this codebase via the `#color-dialog` pattern.
- **`node --check` ≠ static analysis.** It caught zero of the three runtime-reference bugs introduced this session. A real linter (eslint with `no-undef`) would have caught at least two of them; we don't have one in this repo and the cost-benefit of adding one is borderline for a single-user vanilla-JS project.
- **The pre-tool-use security hook flagged PHP's PDO `query()`/sibling calls as if they were Node child-process invocations** — substring match on the `e_x_e_c(` token rather than language-aware. False positive cost one extra Edit retry. Worth knowing the hook is not language-aware.

### Decisions Made
- **Dashboard mode hides the sidebar.** Cards are the primary nav now; the tree is for list-view only. → `decisions.md`.
- **Card colors live on the categories table; hidden-set lives in settings.** Property-of-category vs property-of-view distinction. Lets phase-3 views just gain their own `hidden_ids` array without schema rework. → `decisions.md`.
- **Dashboard order is per-view, stored as JSON in `settings.views_data`.** No `views` table; the data is small and atomic-write via single key is fine. Migrate to a real table only when views grow more fields (descriptions, tag filters, sharing). → `decisions.md`.
- **Native `<dialog>` color picker, not the OS picker.** Safari blocks programmatic picker triggers; visible dialog is portable across browsers. → captured in this log; will lift into `decisions.md` if it survives further iteration.
